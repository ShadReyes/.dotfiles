## Figma first: what this checkout proves

1. The shared README declares **14 official Figma MCP skills**, upstream plugin version **2.2.155**, originating at `figma/mcp-server-guide` commit **`2b85b7d27bd6ee124667fcfe88856f6b1f81671a`**. It directs maintainers to preserve the complete `skills/` tree, upstream `figma-*` names, and the local `skills: "./skills/"` declaration. This is the approved repository declaration, not an independently established history of every file. [R2]
2. The checked-in `skills/figma/.claude-plugin/plugin.json` contains `name: "figma"`, `version: "2.2.155"`, and `skills: "./skills/"`. The inspected bundle has `.claude-plugin/` and `skills/`; the manifest declares **no MCP server, hooks, agents, or executable extension**. The README explicitly says MCP is configured separately. Therefore this local package is skills-only; the existence of a Figma MCP connection elsewhere cannot be inferred from this manifest. [R2,R3]
3. `sync-skills.sh` makes one symlink per immediate `skills/*/` directory into **both** `~/.claude/skills` and `~/.agents/skills`. For Figma that is a link to the **bundle**, not fourteen flattened per-skill links. The script does not invoke a plugin installer, add a marketplace, enable a plugin, configure MCP, or register OMP custom directories. It also exposes every immediate source directory, independently of Skillset profile selection. [R1,R2]
4. **Important current-Claude distinction:** a bundle linked under `~/.claude/skills/` that contains `.claude-plugin/plugin.json` can be loaded in place as `figma@skills-dir` under current documented Claude behavior. That is a plugin origin, **not a marketplace install receipt**. It can default on, subject to settings/policy. Thus “the sync script never runs a plugin installer” does **not** imply “Claude cannot load the folder as a plugin.” Actual symlink existence, policy, and loaded state were not inspected. [C1,C3]
5. The shared Pi manifest exposes `skills: ["."]` for the whole library. A Pi local-package declaration could therefore expose the same physical Figma files already reachable through the shared symlink pool; physical-path deduplication is relevant, while copied independent files instead enter name-collision handling. [R4,P2,P3,P5]
6. OMP's documented repository convention points `skills.customDirectories` at `skills/figma/skills`. This is the correct **shape** for OMP's one-level scanner; the README instruction is not proof that the setting is currently present or that a plugin manager installed Figma. [R2,O1,O2]
7. **Naming is not universal:** current Claude plugin loading yields names such as `figma:figma-use`; current Codex source can also derive that prefix from the Figma manifest during local discovery; Pi uses `figma-use`; OMP normally uses `figma-use` and introduces `figma/figma-use`-style names only when differing same-name skills collide. A filename layout or preserved `name` field alone does not determine the final cross-harness address. [C1,X5,X6,O1,P2]

**Current Figma installation status: unverified.** No plugin registries, settings, caches, symlink pools, enabled-provider state, sessions, or MCP configuration were read. This deliberately leaves marketplace-installed, skills-directory-loaded, enabled, and runtime-loaded states distinct. No private configuration dump or broad manager listing was needed to establish the package capabilities.

## Claude Code

### Roots, traversal, and naming

Observed in Anthropic's current documentation:

- Enterprise skills live in the managed settings directory's `.claude/skills`; personal skills in `~/.claude/skills`; project skills in `.claude/skills`. A directory added with `--add-dir` or `/add-dir` contributes its `.claude/skills`. The `permissions.additionalDirectories` setting alone grants access, not discovery. Plugin skills come from the enabled plugin's default `skills/` and manifest-declared skill directories. [C1,C2]
- Plain-skill child folders can be symlinks to external directories; repeated locations pointing to the same target load once. This documented child-link contract should not be expanded into an untested assertion about replacing the **whole skills root** with a symlink. Plugin component symlinks are subject to plugin-root containment rules and marketplace-specific exceptions. [C1,C3]
- Project roots are searched from the launch directory upward to the repository/worktree boundary. Nested `<subdir>/.claude/skills` load when Claude first reads/edits files there, and remain available. On v2.1.257+ `/add-dir` can load them earlier. This is not the same operation as recursively scanning arbitrary `<skills-root>/group/category/skill` layouts. The documented plain/plugin layout is child skill folders (or an explicitly declared folder containing `SKILL.md` directly); arbitrary deeper taxonomy support remains unverified here. [C1,C2]
- Frontmatter `name` or folder name sets the skill command. The directory name can remain an invocation alias for plain skills. Plugin prefixes remain in place; current docs also describe an unconflicted bare-name alias. For plugin frontmatter already carrying its own prefix, v2.1.246+ avoids adding the prefix twice. [C1]
- For same-named plain skills: enterprise wins over personal, personal over project; a skill beats an old `.claude/commands` file. Root and nested project skills can both remain reachable with directory-qualified variants. Added-directory collisions retain a prefixed variant (the documented added-directory naming requires v2.1.309+). A plugin skill and a plain skill both load because the plugin has a namespace; namespace separation is **not duplicate-content elimination**. [C1]

### Granularity, coexistence, and reload

- `skillOverrides` offers `on`, `name-only`, `user-invocable-only`, and `off`. `off` blocks invocation through the skill interface as well as hiding the command. Anthropic explicitly says **plugin skills are not affected**. It is not a per-plugin-skill selection API. [C1]
- Frontmatter `disable-model-invocation: true` prevents autonomous use; `user-invocable: false` prevents user-command use. Neither should be described as filesystem isolation or a mechanism that removes the skill file from the model's permitted file access. Changing third-party frontmatter would be a source-content modification, not a manager-side install filter. [C1]
- Plugin enablement is by plugin ID, with settings scope precedence. The plugin may contribute skills, agents, hooks, MCP, and other components. Disabling the whole plugin is therefore not a skills-only operation. `skills` manifest paths add to the default `skills/` scan; an empty additional-path list is not documented as a consumer switch for suppressing the default skill component. [C2,C3]
- **Inference:** when an independently exposed plain skill duplicates a plugin skill, retaining the plugin and excluding only the plain exposure can preserve the plugin's unrelated capabilities. The inverse—retaining every plugin capability while suppressing arbitrary bundled skills through `skillOverrides`—is expressly unsupported by that setting. No general consumer-side per-plugin-skill filter was established in the reviewed docs. [C1–C3]
- Claude watches existing personal/project/launch-added skill roots for `SKILL.md` additions, edits, and removals, except in bare mode. A newly created top-level skills root needs `/reload-skills`, and subsequent changes there may need it again. Changes to a skills-directory plugin's hooks/MCP/agents/output styles need `/reload-plugins`; plugin installation/update/enablement becomes active at plugin reload or restart. Already inserted skill text is not retroactively erased from conversation history by changing discovery. [C1,C3]

## Codex CLI

### Roots, recursion, identity, and namespaces

- Official docs specify repository `.agents/skills` roots between CWD and repository root, user `~/.agents/skills`, admin `/etc/codex/skills`, and bundled system skills. Current source additionally retains deprecated `$CODEX_HOME/skills`, config-layer-derived skill roots, supplied extra roots, and enabled-plugin roots. Do not equate the newer recommended `.agents` convention with removal of legacy discovery. [X1,X3]
- Host discovery defaults to recursive mode. At the pinned source it is bounded by **depth 6**, **2,000 directories**, and **20,000 entries per root**; hidden directories are skipped. Directory symlinks are followed for user/repository/admin scope, not system scope. Agent Plugins using `DirectChildren` mode use a different traversal contract; “Codex recursively scans every plugin format” would be false. [X4]
- Source canonicalizes skill identity and merges by canonical `SKILL.md` path; the first occurrence of that identity survives. Different files with the same name survive and can appear in selectors. Scope/name/path sorting is ordering, not a promise that a higher-scope same-name file suppresses the others. Explicit structured/path selection can disambiguate; the plain `$name` selection code refuses an ambiguous skill name rather than arbitrarily selecting the first. [X4,X6,X8]
- Current source's namespace resolver uses the nearest matching plugin namespace, including nested/canonical symlink roots, or an owning plugin's supplied namespace. It qualifies a skill as `plugin:skill`. Compatibility code recognizes `.claude-plugin/plugin.json` as a discoverable manifest; this namespace can therefore arise from a local bundle without proving plugin-manager installation. This is source-snapshot behavior, not a verified property of the installed Codex release. [X5]

### Granularity, coexistence, and reload

- `[[skills.config]]` accepts exactly one selector: absolute canonicalized `path` to `SKILL.md`, or exact `name`. A name matches every skill with that final name; later matching rules win. At the pinned source these rules are gathered from **user and session-flag layers**, not general project layers. The separate bundled-skills toggle can be project-scoped. [X1,X7]
- Skill rules are applied after loading and merging the full host inventory, including plugin roots. **Inference supported by that separation:** a path rule can disable a plugin skill without disabling that plugin's MCP/other inventory; a name rule is broader and can affect multiple same-named copies. Conversely, CLI `/plugins` on/off is a whole-plugin control, not a selective skill control. This establishes host capability, not a choice to exercise it for Figma. [X2,X3,X7]
- A copied plugin skill and independently copied local skill are not guaranteed to collapse merely because their bodies match. Symlink/canonical-path deduplication solves only same-file identity. Plugin qualification may distinguish names but does not prove that the content was exposed only once. [X4–X6]
- Official docs say skills are detected automatically; restart if an update/new installation does not appear. They explicitly require restart after skill configuration changes and a new session after CLI plugin install. This report does not promise that every external symlink retarget, plugin cache replacement, or configuration edit is hot-reloaded in every Codex client/version. [X1,X2]

## OMP

### Roots, traversal, and collision resolution

- Native roots are user `~/.omp/agent/skills` and ancestor project `.omp/skills`, closest project first. Conventional providers also support Claude, Agents (`.agent[s]/skills`), Codex, plugin sources, and other ecosystems. Foreign **user** providers are opt-in through `enabledProviders`; native/project and OMP-owned marketplace sources have distinct defaults. Merely having a Claude install record is not proof OMP admitted its skills. [O1,O3,O5]
- Conventional roots and `skills.customDirectories` scan `<root>/<name>/SKILL.md` only. Child symlinks are accepted; the scanner does not descend arbitrary nested bundles. Claude-plugin manifest paths may also designate a directory containing `SKILL.md` directly. Native/custom scans require descriptions. [O1,O2]
- Provider priority is not a universal plugin namespace: native 100, Skillshare 95, OMP extension packages 90, Claude 80, Agent Plugins 75, Claude-plugin/Agents/Codex 70, then lower-priority providers. The skill loader examines the pre-dedup inventory, deduplicates realpaths, and collapses same-name copies with identical body **and deeply equal parsed frontmatter**. A modified frontmatter copy is not necessarily identical for this purpose. [O1]
- Differing same-name skills retain one bare name; others receive `<namespace>/<name>`, with `~2`, `~3`, etc. as necessary. Custom-directory skills outrank ordinary provider copies; authored skills outrank registry-installed Skillshare packages; among custom directories the first keeps the bare name. Plugin identity supplies a collision namespace where available. Non-colliding plugin skills do not all get prefixes. Raw frontmatter names containing `/` or `\` are rejected. [O1,O2]

### Granularity, coexistence, and refresh

- `skills.enabled: false` stops skill discovery. Individual source controls include `enableClaudeUser/Project`, `enableCodexUser`, `enableAgentsUser/Project`; the historical `enablePiUser/Project` names gate the **native** provider in current loader code. These are skill-source controls, not evidence that a matching MCP source was disabled. [O1,O4]
- `disabledExtensions` entries `skill:<name>` and `skills.ignoredSkills` exclude by raw and final name; `skills.includeSkills` is applied to the resolved final names. Raw-name exclusion can remove all collision variants, so it is not inherently an origin-specific selector. `manualSkills` globs hide skill catalog entries but keep `skill://` and explicit skill-command access. [O1,O4]
- OMP's Claude-plugin provider discovers skills and MCP as separate capability surfaces from allowed plugin roots. Whole-plugin disable/registry selection can remove both; filtering skills in the skill loader does not itself disable the plugin's MCP capability. **Inference:** this separation permits avoiding selected skill exposure while preserving unrelated plugin/MCP capabilities, provided selection targets the actually resolved names. Namespace assumptions alone are insufficient. [O1,O5]
- Discovery is primarily startup-based. Current `skill://` handling can rediscover on an unknown name, rate-limited to one pass per two seconds, and recover stale/superseded plugin paths. The main session can refresh its list/system prompt; inherited fixed subagent lists do not gain newly added skills. This is not equivalent to a guaranteed live watcher for all changed roots/settings. The repository's instruction to restart after discovery-configuration changes remains a convention, and no live configuration reload was tested. [O1,O6,R2]
- `skill://` can also fall back to an MCP-advertised resource **when no loaded local skill owns that name**. Local ownership wins. Therefore local installed skills and MCP-served instruction resources are distinct discovery paths even when both concern Figma; this does not authorize taking over MCP configuration. [O1,O6]

## Pi

### Roots, recursion, and duplicate precedence

- Current Pi loads native user `~/.pi/agent/skills`, trusted project `.pi/skills`, user `~/.agents/skills`, ancestor project `.agents/skills` up to the repository root, configured skill paths, CLI-supplied paths, and package resources. Project trust gates project resources. Local packages load from their resolved source path without copying. [P1,P3,P4]
- The recursive scanner follows directory/file symlinks, skips dot-prefixed directories and `node_modules`, and respects `.gitignore`, `.ignore`, and `.fdignore`. It treats a directory containing `SKILL.md` as one skill and stops descending below it. Therefore a bundle-level `SKILL.md` can prevent nested skills from being discovered; “recursive” does not mean unconditional traversal of every descendant. Portable directories are preferable to the additional standalone-Markdown forms. [P2,P4]
- Names come from frontmatter or parent directory fallback. Required description failures prevent loading; many name-format violations warn rather than hard-fail. The loader does not add plugin namespaces. It silently deduplicates the same canonical physical file, then keeps the first different-file same-name skill and reports a collision. Identical copied text is not a separate content-deduplication contract. [P2,P5]
- “First” is resource-discovery order, not an invariant that user always beats project. Current automatic enumeration adds trusted project `.pi` skills, ancestor `.agents` skills, native user skills, then shared user skills; packages and CLI resources participate through the resource loader as well. The loader's old convenience `includeDefaults` sequence must not be mistaken for the full interactive package resolver's precedence. [P2,P4]

### Granularity, coexistence, and reload

- A package settings object can narrow each resource type independently: omitted means all package-allowed resources; `[]` means none of that type; `!pattern`, `+path`, and `-path` exclude/include paths. Setting a package's `skills: []` leaves its independently declared extensions/prompts/themes eligible. Global/project resource lists also support exclusions, and `pi config` manages discovered resources. [P3,P6]
- `disable-model-invocation: true` leaves explicit `/skill:name` access while removing automatic model listing. `enableSkillCommands` controls interactive command discovery; current skill docs say manually entered skill commands still work. Neither is equivalent to removing the skill resource. [P1]
- Current Pi's built-in MCP integration is an independently controlled extension (`builtin:mcp`); skill resource filtering does not inherently disable it. A Claude `.claude-plugin/plugin.json` is not a Pi `package.json` resource manifest. Recursive loading of its `SKILL.md` files does not establish that Pi installed or enabled the Claude plugin's other capabilities. [P2–P4,P6]
- `/reload` reloads skill/resources/settings. Package docs warn that reload may also retry failed package installation and reconcile temporary `-e` remote sources; pinned commit sources are treated differently from moving refs. No reload was invoked in this investigation. This is relevant operational behavior, not a recommendation to introduce automatic upstream updates. [P1,P3,P4]

## Library-wide conclusions and remaining unknowns

### Facts established, not policy choices

- **Registration, discoverability, enablement, loading, and invocation are different states.** Shared-library presence and a plugin-compatible manifest establish packaging, not current plugin-manager installation or runtime activation. Current Claude adds an important non-marketplace `@skills-dir` loading route. [R1–R4,C3]
- **Symlinks avoid file copies, not every form of duplicate exposure.** Same-file deduplication differs from name collision handling and content equality. Cross-harness namespaces and precedence are not interchangeable. [C1,X4–X8,O1,P2,P5]
- **There is no uniform per-skill plugin switch across these four harnesses.** Codex merged-inventory skill rules, OMP skill filters, and Pi per-resource filters provide finer granularity than disabling their whole packages. Claude's documented `skillOverrides` explicitly excludes plugin skills. All can retain a plugin while an independent duplicate route is withheld; which route should remain is deliberately undecided. [C1,X7,O1,P3]
- The repository's global-name uniqueness rule remains a stated shared-library convention, not a claim that every harness ignores plugin metadata. Its Pi motivation matches current first-name-wins behavior. Conversely, a library-wide unique raw name does not prevent the same skill being exposed twice through independent physical installations. [R2,P2,X5]

### Unknowns / limits

1. Installed versions, enabled sources, effective settings scopes, trust/policy restrictions, actual linked roots, plugin registry/cache entries, and current session catalogs are **unverified**. No actual private source identifiers, paths, remotes, or content were inspected or published.
2. Figma marketplace-installed vs skills-directory-loaded vs enabled vs runtime-active state is **unverified**. The local bundle manifest and approved README declaration alone cannot distinguish them.
3. Anthropic docs are mutable and Claude implementation source was not audited. Arbitrary deeper plain-skill taxonomy traversal, whole-root symlink behavior, and identity deduplication across an installed plugin cache and an unrelated plain source are **not established** here. Do not infer them from child-link support.
4. The open-source snapshots can be newer than installed releases. Codex's namespace recognition, selector behavior, traversal limits, and Pi's package/trust/MCP behavior must be interpreted at the cited commits rather than assumed for every historical release.
5. Live symlink-retarget watching, every plugin-format/path edge case, already-running subagent refresh, and retroactive removal of instruction text were not experimentally verified. Reload guidance above reports owning docs/source, not a smoke-test result.
6. This report does not select ownership, desired-vs-active exposure, a migration strategy, automatic upstream refresh, or which unrelated plugin/MCP capabilities to retain or replace.
